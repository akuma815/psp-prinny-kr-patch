## 1. 반드시 지킬 작업 규칙

1. 원본 ISO와 깨끗한 `extracted` 원본은 직접 수정하지 않는다.
2. 변경은 작업 트리 또는 별도 빌드 폴더에서 수행한다.
3. 충분히 검증되기 전에는 ISO를 만들지 않는다.
4. 우선 `work\builds\direct_run_latest`를 PPSSPP에서 직접 실행해 검증한다.
5. 오래된 세이브스테이트로 런타임 성공을 판정하지 않는다. 새 부팅을 정본으로 삼는다.
6. 사용자 스크린샷과 실제 런타임 결과를 정본으로 취급한다.
7. PPSSPP 프로세스를 종료해야 할 때는 확인한 정확한 PID만 종료한다. 광역 종료 명령을 쓰지 않는다.
8. 기존 산출물, 사용자가 만든 CSV/JSON/PNG, 텍스처 팩을 덮어쓰기 전에 보존본을 만든다.
9. 확인된 사실, 기각된 가설, 미검증 가설을 문서에서 분리한다.
10. 의미 있는 변경 뒤에는 관련 `docs\*.md`와 최신 인계서를 갱신한다.

## 3. 사용자가 확인한 현재 증상

타이틀 설정의 네 항목은 다음과 같다.

```text
SE 음량
BGM 음량
음성 음량
카메라 회전
```

정상 번역 설명은 다음과 같다.

```text
SE:
  【일반】 게임 내 SE 음량을 바꿉니다.

BGM:
  【일반】 게임 내 BGM 음량을 바꿉니다.

음성:
  【이벤트】 음성 메시지 음량을 바꿉니다.

카메라:
  【전투】 프리니 연사 때 카메라 회전 여부를 설정합니다.
```

실제 증상:

- 새 부팅 직후 한두 번은 올바른 설명이 표시될 수 있다.
- 선택을 반복하면 SE, BGM, 카메라 설명이 다른 항목의 설명 또는 잘못 합쳐진 문자열로 바뀐다.
- 한 번 잘못된 값이 선택되면 이후에는 그 잘못된 값으로 안정적으로 반복되는 경우가 많다.
- 음성 설명은 다른 세 항목보다 정상으로 유지되는 경우가 많았다.
- 띄어쓰기만 어긋나는 경우와 서로 다른 설명 조각이 합쳐지는 경우가 모두 관찰됐다.

이 패턴은 단순 번역 누락이 아니라 동적 글자 atlas 또는 에뮬레이터 텍스처 캐시 상태에
의존하는 문제다.

## 4. 기각된 가설

### 4.1 번역문이 원문 슬롯보다 길어서 다음 문자열을 침범한다

**기각됨.**

- 네 설정 설명을 원문 CP932 바이트 길이와 정확히 같게 만든 대조군에서도 동일 증상이 재현됐다.
- 대조 문자열은 표시 문자를 모두 2바이트 문자로 제한하고 부족한 길이를 전각 공백으로 채웠다.
- 따라서 단순 슬롯 초과와 1/2바이트 혼합 길이 계산만으로는 현상을 설명할 수 없다.

관련 자료:

```text
work\diagnostics\boot_ui_exact_source_length_20260727\
  boot_ui_translation_exact_length.json
  exact_length_report.json

work\analysis\verify_boot_ui_exact_length_control.json
```

### 4.2 커스텀 글리프 셀 재사용 훅만이 원인이다

**단독 원인으로는 기각됨.**

- 글리프 중복 셀 재사용, 페이지별 카운터 동기화, 보조 UI 페이지 wrapper, reset helper를
  모두 제거한 네이티브 atlas 대조군에서도 사용자 화면에서 증상이 재현됐다.
- 현재 `direct_run_latest`가 바로 이 네이티브 atlas 대조군이다.

### 4.3 CPU 문자열 포인터 또는 번역 슬롯 자체가 잘못 선택된다

**현재 설정 설명 경로에서는 가능성이 매우 낮다.**

- 문자열 setter, 복사 직전 버퍼, 렌더러 입력, 글리프 ID를 단계별로 추적했다.
- 선택 항목에 맞는 소스 포인터와 문자열이 렌더러까지 정상 전달됐다.
- 아래 GPU 덤프에서도 선택 변경에 따라 실제 atlas 내용과 글자 draw 수가 달라진다.

## 6. GPU 명령 스트림에서 새로 확정한 사실

PPSSPP 원격 디버거의 `gpu.record.dump`로 실제 GE 프레임을 저장하고, 32,768바이트 atlas
텍스처와 글리프 vertex packet을 짝지어 비교했다.

### 기존 연속 캡처

```text
work\analysis\ppsspp_gpu_transitions_retry_20260727
```

확인 결과:

| 프레임 | 설명 draw 수 | atlas SHA-256 앞부분 |
| --- | ---: | --- |
| 선택 전 | 21 | `20ad2a...` |
| 아래 1회 | 27 | `4fe7f8...` |
| 아래 2회 | 21 | `20ad2a...` |
| 아래 3회 | 20 | `2a4485...` |

문자열 길이와 대조하면 다음 항목 변화와 일치한다.

```text
SE 또는 BGM: 21 glyph draw
음성:        27 glyph draw
카메라:      20 glyph draw
```

각 프레임의 atlas SHA-256, cell SHA-256, UV가 함께 바뀌었다. 즉:

1. 번역 문자열이 렌더러까지 정상 도착한다.
2. 게임은 선택 변경 때마다 서로 다른 올바른 atlas bitmap을 만든다.
3. GE draw command도 해당 atlas와 UV를 참조한다.
4. 화면에서만 이전 또는 잘못된 글자가 보이는 분기는 GE 명령 생성 뒤쪽에 있을 가능성이 높다.

### 정지 직전 추가 캡처

```text
work\analysis\ppsspp_gpu_live_ready_20260727
  frame_00_before.ppdmp
  frame_01_down.ppdmp
  frame_02_down.ppdmp
  comparison.json
```

요약:

| 프레임 | 설명 draw 수 | atlas SHA-256 |
| --- | ---: | --- |
| `frame_00_before` | 21 | `20ad2a2eb449729378d9282126d96e3dae8732e19ff51f1652ff44a8f2f36364` |
| `frame_01_down` | 27 | `4fe7f86b2542f91ef191bedd7377d1033af40c46b13c0b6ebb846109a87b5999` |
| `frame_02_down` | 27 | `4fe7f86b2542f91ef191bedd7377d1033af40c46b13c0b6ebb846109a87b5999` |

- 첫 선택 변경에서 21글자 atlas에서 27글자 atlas로 정상 변경됐다.
- 두 번째 캡처는 입력 또는 메뉴 상태가 한 항목에 머물러 같은 27글자 atlas가 기록된 것으로 보인다.
- 연속 캡처 스크립트는 세 번째 이후 PPSSPP 디버거 응답 타임아웃으로 종료됐다.
- 타임아웃 뒤에도 PPSSPP 프로세스는 응답 중이었으므로 게임 크래시로 기록하면 안 된다.
- 이 폴더에는 `manifest.json`이 없다. 중간 종료된 캡처이므로 `comparison.json`과 개별 덤프를

분석 스크립트:

```text

workspace\scripts\compare_ppsspp_gpu_dumps.py
workspace\scripts\capture_ppsspp_gpu_frame.py
```

재분석 명령:

## 7. 가장 유력한 미검증 가설

### PPSSPP 텍스처 교체용 `quick` 해시와 동적 글자 atlas의 충돌 또는 캐시 오인

이것은 **유력하지만 아직 대조 실험으로 확정되지 않은 가설**이다.

정지 시점의 PPSSPP 설정:

```text
실행 파일:
  H:\ppsspp\PPSSPPWindows64.exe

그래픽 백엔드:
  GraphicsBackend = 3 (VULKAN)

ppsspp.ini:
  PauseOnLostFocus = True
  InternalResolution = 10
  TextureBackoffCache = False
  ReplaceTextures = True
  SaveNewTextures = True
  InflightFrames = 1

텍스처 팩:
  H:\ppsspp\memstick\PSP\TEXTURES\ULJS00150\textures.ini

textures.ini:
  hash = quick
  ignoreAddress = false
```

근거:

- 게임과 GE 덤프의 atlas bitmap은 선택에 따라 정상 변경된다.
- 실제 화면은 이전 또는 잘못된 설명을 표시한다.
- 텍스처 교체 팩이 켜져 있고 동적 atlas 주소 `0955c100`, `09564140`에 대한 해시 항목이 존재한다.
- `SaveNewTextures = True` 때문에 `ULJS00150\new` 아래에 동적 atlas 덤프가 매우 많이 생성됐다.
- PPSSPP 공식 문서는 `quick` 해시가 불완전하며 새 팩에는 `xxh64`를 권장한다.
- 화면 증상은 짧은 해시가 동적 atlas 변경을 구분하지 못하거나 캐시가 이전 결과를 재사용하는
  경우와 일치한다.

공식 참고:

- `https://www.ppsspp.org/docs/reference/texture-replacement/`
- `https://github.com/hrydgard/ppsspp/issues/19086`

주의:

- `hash = xxh64`로 바꾸면 기존 텍스처 해시 키 전체가 달라진다.
- 따라서 현재 텍스처 팩을 백업 없이 바로 전환하면 정적 이미지 교체가 모두 끊길 수 있다.
- `quick` 상태에서 0 와일드카드 규칙을 섞는 것도 피한다.
- 아직 이 가설을 확정하지 않았으므로 기존 `textures.ini`는 수정하지 않았다.

## 8. 다음 재개 시 가장 짧은 원인 확정 절차

아래 순서를 바꾸지 않는다. 각 대조군은 새 부팅에서 설정 항목을 최소 12회 순환해 판정한다.

### 단계 A — 현재 설정 보존

1. PPSSPP를 종료하기 전에 정확한 PID를 다시 확인한다.
2. 아래 파일을 날짜가 붙은 진단 폴더에 복사해 보존한다.

```text
H:\ppsspp\memstick\PSP\SYSTEM\ppsspp.ini
H:\ppsspp\memstick\PSP\TEXTURES\ULJS00150\textures.ini
```

기존 PPSSPP 설정 백업:

```text
work\analysis\ppsspp_ini_before_direct_trace_20260727.ini
```

### 단계 B — 텍스처 교체 전체 OFF 대조군

PPSSPP 설정에서 진단용으로만 다음을 적용한다.

```text
ReplaceTextures = False
SaveNewTextures = False
```

그 뒤 `work\builds\direct_run_latest`를 새 부팅하고:

```text
SE → BGM → 음성 → 카메라 → SE
```

를 최소 12회 반복한다.

판정:

- 설명이 끝까지 정상: PPSSPP 텍스처 교체/해시/캐시 경로가 원인 범위로 확정된다.
- 동일 증상 재현: `quick` 해시 가설을 기각하고 Vulkan texture cache 또는 원본 GPU upload
  invalidation을 추적한다.

### 단계 C — `xxh64` 진단 대조군

단계 B에서 정상이라면 텍스처 팩을 보존한 뒤 진단 복사본에서만:

```text
hash = xxh64
ReplaceTextures = True
SaveNewTextures = False
```

로 시험한다.

기존 `[hashes]` 키는 `quick` 기준이므로 이 상태에서 기존 정적 교체가 매칭되지 않는 것은
정상이다. 목적은 동적 atlas 설명이 안정되는지만 보는 것이다.

판정:

- `xxh64`에서 설명이 안정: `quick` 해시 충돌/오인이 사실상 확정된다.
- `xxh64`에서도 깨짐: 해시 알고리즘보다 PPSSPP texture replacement/cache invalidation
  자체 또는 Vulkan 경로를 조사한다.

### 단계 D — 필요할 때만 그래픽 백엔드 대조

단계 B에서도 재현될 때만 Vulkan과 OpenGL/D3D11을 같은 새 부팅 조건으로 비교한다.
백엔드 변경은 단계 B와 섞지 않는다.

### 단계 E — 생산 해결책

`quick`이 원인으로 확정된 뒤에만 아래를 진행한다.

1. 기존 텍스처 팩 전체 백업.
2. `xxh64`로 정적 텍스처 해시를 재수집.
3. 기존 번역 PNG를 새 해시 키에 재매핑.
4. 동적 글자 atlas 주소는 교체 대상에서 명시적으로 제외할 방법을 검증.
5. `SaveNewTextures = False`로 복원.
6. 데모 스킵, 스테이지 표지판, UI 고정 이미지, 설정 설명을 모두 새 부팅에서 재검증.

### 14.24 PSP 실기 세이브 화면 즉시 닫힘 — 원인 규명 (2026-07-29)

사용자 피드백: **실기(PSP)에서 세이브 NPC → 세이브 버튼을 누르면 세이브 화면이
아주 빠르게 나왔다 사라진다.** PPSSPP에서는 정상.

**원인 확정 (정적 분석):**

1. PSP 세이브데이터 유틸리티(`sceUtilitySavedata`)의 SFO 파라미터
   (`savedataTitle`, `detail`)는 **UTF-8 문자열**이어야 한다.
2. 게임은 내부 CP932 문자열을 `start.dat`의 **`jis2ucs.bin`** 표로 유니코드
   변환해 넘긴다. 표 구조: **JIS 코드로 인덱싱**되는 65,536×2바이트 배열,
   유효 데이터는 0x0001~0x7426 (ASCII는 항등 매핑, `あ`→U+3042 확인).
3. 우리 한글은 CP932 사용자 정의 영역 **F040~F4BF**를 쓰는데, 이를 JIS로
   변환하면 **0x7F21~0x8841** 구간이고 이 구간은 표에서 **전부 0** →
   **모든 한글이 U+0000으로 변환된다.**
4. 해당 파라미터 문자열 6개가 모두 한글로 번역돼 있다 (BOOT 0x0ED764~0x0ED7C8):
   `시스템 데이터` / `%s 시스템 데이터입니다.` / `게임 데이터` /
   `%s 저장 데이터입니다.` / `리플레이데이터` / `%s 리플레이 데이터입니다.`
5. 즉 실기 펌웨어는 빈/무효 문자열을 받아 즉시 오류 반환 → 다이얼로그가
   떴다가 바로 닫힌다. PPSSPP의 HLE 세이브 구현은 관대해서 드러나지 않았다.

**수정 방향 (택일, 사용자 결정 필요):**

- **A. 표 패치 (권장, 근본 해결)**: `jis2ucs.bin`의 JIS 0x7F21~0x8841 구간에
  한글 코드→실제 유니코드(U+AC00 계열) 매핑을 기록. 해당 구간은 **기존 사용
  0개로 완전히 비어 있어 안전**. 단, PSP 펌웨어 시스템 폰트에 한글 글리프가
  없으면 세이브 목록에 빈칸/네모로 보일 수 있어 실기 확인 필요.
- **B. 해당 6개 문자열만 ASCII 영문으로**: ASCII는 항등 매핑이 검증돼
  변환이 100% 안전(`GAME DATA`, `%s save data.` 등). 실기 폰트 문제도 없음.
- **C. 해당 6개만 일본어 원문 복원**: 가장 보수적, 확실히 동작.

**조치 (C안 채택, 사용자 결정):** 세이브 파라미터 6개만 일본어 원문 복원.

- 사용자가 `original\` 복구 → 해시 `af0d2873...` 일치 확인.

### 14.26 **원인 확정과 해결: NISPACK 섹터 정렬 파괴** (2026-07-29)

**실기 분리 실험 결과 (사용자): DiagA(실행파일만 패치) = 저장 정상,

**원인 확정 (정적 대조):**


모든 멤버를 **원본 오프셋 그대로** 두고, 교체 페이로드를 원래 슬롯 안에 쓴 뒤
남은 공간을 0으로 채우며 헤더의 크기 필드만 갱신한다(슬롯 초과 시 오류).

### 14.27 크기 체인 보존 (start.lzs 제로 패딩) — v1.3 (2026-07-29)

정렬 복구 후에도 실패해 SYSTEM.DAT의 남은 차이를 재조사한 결과:

```text
원본은 모든 멤버에서 align(offset + size, 2048) == 다음 멤버 offset 이 성립
  start.lzs: 0x50000 + 3,630,771 -> 올림 0x3C6800 == UMD_PIC1 위치 ✓
우리 빌드(v1.2): 오프셋 표는 원본과 같지만 size가 3,576,699로 작아
  0x50000 + 3,576,699 -> 올림 0x3B9800 ≠ 0x3C6800 (53,248B 어긋남)
```

즉 게임이 오프셋 표가 아니라 **앞 멤버의 크기로 다음 위치를 순차 계산**하면
세이브 아이콘(PRINNY_ICON0.PNG)을 엉뚱한 곳에서 읽게 된다. ANIME/BG는
`replace_nispack_fixed`가 크기·위치를 모두 보존해 이 문제가 없었다(검증 완료).

**해결**: `build_direct_run.py`에서 재압축된 start.lzs를 **원본 압축 크기까지
0으로 패딩**해 NISPACK 저장 크기를 원본과 동일하게 만든다. LZS 헤더가 자체
압축 크기를 갖고 있어 뒤쪽 0은 디코딩되지 않는다(패딩 시 우리 디컴프레서의
strict 검사에 걸리므로 self-roundtrip은 패딩 전 스트림으로 수행).
빌드 리포트에 `stored_size`/`zero_padding` 필드 추가.

검증: SYSTEM.DAT의 **7개 멤버 오프셋·크기가 원본과 완전히 동일**,
크기 체인도 원본과 동일하게 성립. 파일 크기 4,127,307B 동일.
슬롯 590/590 PASS, 부팅 프로브 PASS.

**배포본 v1.3:**

```text
ISO SHA-256: e028bab8bcf9296715c3a494cb293a3db2cd4400fb890a5a2bc743ed284b70ea
xdelta 재생성 + 왕복 검증 완료, README 해시 갱신, SHA256.txt v1.3
```

**v1.3 실기 결과: 여전히 실패.** 크기 체인 가설도 단독 원인은 아니었다.

### 14.35 **근본 원인 확정과 수정: 복사 헬퍼의 41바이트 무조건 삭제** (2026-07-29)

**7차 실기 결과 (사용자): DiagL(케이브 코드는 있으나 훅 미설치) = 세이브 정상.**

→ 코드 **배치**는 무해하고, 헬퍼가 **실행될 때** 깨진다는 것이 확정됐다.

**코드 리뷰로 버그 발견 — `COPY_HELPER_ASM` 도입부:**

```asm
    move  $t2, $a0
    addiu $t3, $zero, 0x29     ; 41
copy_clear:
    sb    $zero, 0($t2)        ; 목적지에서 41바이트를 무조건 0으로 삭제
    ...
```

원본 게임 코드에는 없는 동작이다. 원본은 `strncpy(dest, src, count*2)` 후
`sb zero, dest+count*2`로 **복사한 만큼만 쓰고 끝에 종료자**를 넣는다.
우리 헬퍼는 그 전에 목적지 뒤 41바이트를 무조건 파괴하고 있었다.
실기 펌웨어는 이렇게 오염된 세이브 파라미터를 받으면 다이얼로그를 즉시
닫고, PPSSPP는 관대해 드러나지 않았다 — 관측된 모든 증상과 일치한다.

**수정**: `copy_clear` 루프 제거. `copy_done`이 복사 종료 지점에 정확히
NUL을 쓰므로 종료 처리는 원본과 동등하다. 케이브 사용량 316바이트.

역어셈블로 확인한 원본 리빌 루프 구조 (참고):

```text
0x088653A0 jal strlen        / 0x088653A4 lw a0,24(s3)   ← 소스 문자열
0x088653AC sra v1,v0,1       ← 문자 수 = 길이/2 (2바이트 전제)
0x088653D8 addu a0,s2,zero   ← 목적지 버퍼
0x088653E8 jal strncpy       / 0x088653EC sll a2,v0,1    ← 바이트 수
0x088653F8 addu v0,s2,v0     / 0x088653FC sb zero,0(v0)  ← 종료자
```

**8차 산출물:**

```text

  전체 한글 패치 + native_reveal(대사 보정 유지) + 41바이트 버그 수정
Candidate_v14_native_full.iso       (19313a87...)  안전 대안(보정 제외)
DiagN_hook_fixed_helper.iso                        수정본 실행파일만 적용
```

모두 부팅 프로브 PASS. 자동 테스트는 기존 2건(삭제된 폴더 참조)만 실패.

### 14.36 **근본 원인 확정: 한글이 U+0000으로 변환** — 변환표 패치 (2026-07-29)

**8차 실기 결과 (사용자): DiagN 정상, v15 실패.**

여기서 실험 설계의 허점이 드러났다. **지금까지 "정상"이 나온 진단 빌드
(DiagJ/K/L/N)는 모두 `clean BOOT`에 ASM만 적용한 것이라 한글 BOOT UI
텍스트가 없었다.** 즉 한글 텍스트 자체는 단독 검증된 적이 없었고,
"실행파일 무죄" 판정은 텍스트를 제외한 범위에서만 성립했다.

**원인 확정**: PPSSPP가 만든 세이브의 `SAVEDATA_DETAIL`을 열어 보니

```text

プレイ時間：00:07:55
```

즉 세이브 설명문은 BOOT UI 문자열로 조립된다. 소스 슬롯을 특정했다:

```text

0x0F0ADC~0x0F0B6C  残り○魔時間 10종 (첫 %s)
```

이들은 전부 한글로 번역돼 있었고, 게임은 이를 `jis2ucs.bin`으로 유니코드

- 대상 슬롯은 원본에서 전부 0이라 **충돌 0건**이며 일본어 매핑은 불변
  (빌드 산출물에서 `가`→U+AC00, `あ`→U+3042 동시 확인).
- 빌드 리포트에 `details.unicode_tables` 추가(987자, 두 표 SHA-256).

게이트: 슬롯 590/590 PASS, 부팅 프로브 PASS, 자동 테스트는 기존 2건만 실패.

```text
Candidate_v14_native_full.iso    (19313a87...)  안전 대안
```

실기 확인 요청: ①세이브 가능 여부 ②세이브 목록의 설명문 표시 상태

### 14.38 **최종 해결과 배포본 v2.0 확정** (2026-07-29)

실기 세이브 실패의 최종 원인은 **PSP 세이브 목록에 표시되는 SFO 문자열
(제목·항목명·설명문)이 한글이라 펌웨어가 저장을 거부**한 것이었다.
