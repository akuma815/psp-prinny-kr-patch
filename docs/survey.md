### SURVEY-ARCHIVE-001 — NISPACK 아카이브

`ANIME.DAT`, `BG.DAT`, `SCRIPT.DAT`, `STAGE.DAT`, `SYSTEM.DAT`에서 `NISPACK\0\0\0\0\0` 시그니처가 확인됐다. 각 파일은 리틀엔디언 항목 수와 44바이트 엔트리 테이블을 가지며, 모든 엔트리의 범위가 파일 안에 있고 상호 겹치지 않았다.

공개된 [tonypolik/nispack 원본 구현](https://github.com/tonypolik/nispack/blob/master/lib/nispack.rb)은 동일하게 32바이트 이름, 32-bit 시작 오프셋, 32-bit 크기, 미사용 처리하는 마지막 4바이트를 읽는다. 이 교차 확인은 테이블 경계에 대한 근거이며, 마지막 4바이트의 의미까지 확정하지는 않는다.

### SURVEY-LZS-001 — start.lzs

`SYSTEM.DAT`의 `start.lzs`는 다음 헤더를 가진다.

| 필드 | 값 |
| --- | ---: |
| 확장자 표지 | `dat` |
| 해제 크기 | `9,030,752` bytes |
| 저장 크기 필드 | `3,630,767` (`파일 크기 - 4`) |
| 이스케이프 플래그 | `0xD5` |

로컬 해제 스크립트가 전체 입력을 소비하고 선언 크기와 정확히 같은 `start.dat`를 만들었다. [tonypolik/nis_lzs의 원본 소스](https://github.com/tonypolik/nis_lzs/blob/master/index.js)는 같은 16바이트 헤더와 이스케이프/역참조 해제 규칙을 구현하며, [프로젝트 README](https://github.com/tonypolik/nis_lzs)는 이 형식이 Prinny를 포함한 NIS 게임에서 사용된다고 명시한다.

판정: **읽기·해제 PASS**. 압축→재해제 왕복과 게임 소비 호환성은 아직 검증하지 않았다.

### SURVEY-START-002 — start.dat 경계 모델 정정

`BOOT.BIN` VA `0x0888B2D4` 부근의 검색 루프는 이름을 `base + 8 + i×32`, 데이터 포인터를 `base + 4 + i×32`에서 읽는다. 따라서 헤더 `+0x04`가 첫 파일 시작점이고 각 32바이트 인덱스 레코드의 마지막 값은 현재 파일의 끝점이다. 마지막 항목의 0은 EOF다.

판정: 기존 조사기의 “현재 항목 마지막 값 = 현재 시작점” 모델은 **기각**했다. 이 오류 때문에 모든 조사 자산이 한 이름씩 밀렸으며 기존 `BaseTalk.dat`는 실제 `MusicShop.dat`였다. 추출기, 파생 자산, 파서 이름과 문서를 정정했다.

### SURVEY-TEXT-001 — 실제 BaseTalk 고정 레코드

정정된 `BaseTalk.dat`는 848바이트이며 `u16 count=16 + u16 unknown=0 + 16 × 52바이트 record + 12바이트 zero footer`다. 레코드는 `u16 record_id + u16 unknown + 12 × u32 resource_key`이고 ID는 `1..10, 22..27`이다. `workspace/scripts/base_talk.py`가 전 파일을 바이트 동일 왕복한다. 고유 키 72개는 모두 `demo.nsf`의 531개 키 맵에서 스크립트 오프셋으로 해석된다.

`BOOT.BIN`은 VA `0x0888B314`에서 count를 `lhu`로 읽고 본문 `+4`를 전역 `0x08A54BE0`에 저장한다. Capstone 5.0.7은 전역 소비자 VA `0x0883F92C`, `0x0889ED04`의 검색 보폭이 52바이트임을 확인했다.

PPSSPP `v1.20.4-426-gae13b9b3e1`에서 VA `0x0888B32C`에 중단해 count 16, 본문 포인터 `0x0942DF24`를 관찰했다. 포인터의 844바이트는 디스크 파일의 헤더 뒤 844바이트와 정확히 동일했다.

판정: **디스크 경계·52바이트 런타임 소비·무변환 로드 PASS**. 주소 12개의 스크립트 의미와 실제 대사 소비는 미확정이다.

### SURVEY-TEXT-002 — MusicShop CP932 표

기존에 BaseTalk로 기록한 BGM명 표는 `MusicShop.dat`다. 2,768바이트, SHA-256 `9610d46931f27e732a7b28b5be4498ce16289ef87a84c03e9350a4d6786cc1f5`, 30 × 92바이트 레코드이며 21/65바이트 CP932 슬롯 60개가 NUL 종료·0 패딩·재인코딩·전체 왕복을 통과했다. 표본에는 `【ＢＧＭ０５】緑色の迷路`, `【ＢＧＭ２３】ＡＳＡＧＩ　メタモルフォーゼ`가 있다.

판정: `workspace/scripts/music_shop.py`가 읽기 모델을 소유한다. BGM 화면 소비가 확인되기 전에는 번역 writer를 만들지 않는다.

NSF 파일을 일반 Shift-JIS 문자열로 휴리스틱 스캔한 결과는 대부분 반복 바이트가 만든 깨진 문자열이었다. 따라서 NSF가 평문 대사를 직접 저장한다고 볼 근거는 현재 없다.

### SURVEY-FONT-001 — 폰트 후보

`BOOT.BIN`의 평문 문자열에 `font.fnt`, `font.txp`가 존재하고, 두 항목은 실제 `start.dat` 인덱스에도 있다. 같은 인덱스에는 `jis2ucs.bin`과 `ucs2jis.bin`도 있다.

판정: `font.fnt`·`font.txp`와 두 변환표가 문자·글리프 경로의 우선 조사 대상이다. 파일명이 실제 렌더 경로를 증명하지는 않으므로, 화면 출력과 소비 코드를 연결하기 전에는 활성 폰트로 확정하지 않는다.

## 6. 현재 판정

**조건부 GO — 역공학과 최소 PoC 준비 단계로 진행 가능.**

NISPACK 읽기, LZS 해제, Demo00 본문 소비와 폰트 맵·글리프 캐시 경로를 확보했고 한글 픽셀의 실제 화면 도달도 확인했다. 단일 레코드의 고정 슬롯 재삽입과 동일 크기 ISO·Headless 부팅까지 통과했지만, 전체 텍스트 모집단의 안전한 코드 공간과 생산용 인코딩·가변 재패킹은 배포 가능 수준으로 확정되지 않았으므로 번역 전량 작업과 최종 폰트 제작은 보류한다.

실제 `BaseTalk.dat`의 52바이트 소비 게이트, 72개 키의 `demo.nsf` 해석, NSF 메시지 명령→ID 소비 형식, 1,431건의 블록 로컬 명령 시작점, `Demo00.dat`와 `MusicShop.dat`의 CP932 가역 파서 게이트는 통과했다. 본문 폰트의 저장·맵·캐시 소비 구조와 단일·다중 한글 글리프의 실제 UI 및 Demo00 명패·본문 도달도 확인했다. Demo00 `0x07D0`의 번역·재삽입 Expected Write, ISO 생성, Headless 부팅과 실제 번역 대화 화면도 통과했다. 다음 승인 게이트는 생산용 코드 공간·매핑 설계이며, NSF 잔여 런타임 검산과 MusicShop 화면 소비 확인도 잇는다.

### SURVEY-RUNTIME-001 — NSF 메시지 핸들러 추적 기준선

PPSSPP `v1.20.4-426-gae13b9b3e1`에서 원본 `ULJS00150` version `1.01`을 재시작하고 메시지 핸들러 세 곳을 90초 관찰했다. `start`·`circle`·`cross` 자동 입력 44회를 보냈으나 핸들러 적중은 0건이었다. 자동 입력이 실제 대화 장면 진입을 보장하지 않으므로 이 결과로 후보를 폐기하지 않는다.
