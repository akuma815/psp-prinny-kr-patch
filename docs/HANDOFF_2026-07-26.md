## 2. 절대 지켜야 할 작업 규칙

1. 원본 ISO와 깨끗한 추출 원본은 절대 직접 수정하지 않는다.
2. 모든 변경은 복사한 작업 트리 또는 별도 빌드 폴더에서 수행한다.
3. 당분간 ISO를 만들지 않는다.
4. 먼저 PPSSPP에서 폴더를 직접 실행할 수 있는 통합 테스트 폴더를 만든다.
5. 텍스처 교체 검수와 게임 파일에 영구 삽입된 결과 검수를 구분한다.
6. 최종 영구 삽입 검수 때는 PPSSPP 텍스처 교체를 끈다.
7. 새 테스트 ISO를 만들게 되면 이전 테스트 ISO는 삭제하고 최신본 하나만 남긴다.
8. 원본 ISO, 원본 추출 트리, 최종 배포 후보는 삭제하지 않는다.
9. 사용자가 직접 수정한 CSV/JSON/PNG는 정본으로 취급하며 덮어쓰기 전에 반드시 보존한다.
10. 작업이 끝날 때마다 관련 `docs/*.md`와 이 인수인계 문서를 갱신한다.
11. 확인된 사실과 추정을 문서에서 구분한다.
12. 사용자가 직접 PPSSPP를 실행하고 스크린샷을 제공하는 방식을 우선한다. 자동 실행·캡처 반복은 느려 중단했다.

## 5. 지금까지의 주요 작업 이력

### 5.1 프로젝트 구조 정리

- 루트의 `Font`, `Tools`, `Games` 구조를 조사했다.
- 신규 게임 한글화 때 참고할 수 있는 구조 가이드 문서를 작성했다.
- Prinny 게임 폴더도 가이드에 맞게 재구성했다.
- 추출물, 번역 원본, 작업 파일, 빌드 파일, 문서를 구분했다.
- 이후 모든 작업에서 관련 문서를 갱신하기로 사용자와 합의했다.

### 5.2 PSP 게임 구조 및 폰트 조사

- PPSSPP 실행 위치는 `H:\ppsspp`다.
- 한글 한 글자 `가`부터 런타임에 넣어 출력 경로를 검증했다.
- 여러 한글 글자를 넣어 폰트 매핑과 대사 출력 경로를 확인했다.
- 사용자가 `HancomMalangMalang-Regular.ttf`를 추가했다.
- 사용자가 제공한 한컴 서체 사용범위 이미지에서 기기 탑재 및 폰트 임베딩 사용 가능으로 확인했다.
- 한글 폰트 생성은 한컴 말랑말랑 계열을 기준으로 진행한다.

### 5.3 번역 스타일 확정

- 프리니 말투는 `임다/임까` 계열을 기본으로 한다.
- `음다/슴다`는 무조건 한 형태로 통일하지 않고 문맥에 자연스러운 것을 선택한다.
- 사용자 승인 예:

```text
없슴까?
그렇게 쉽게 되진 않을 거야.
굳세게 살겠슴다.
```

- 용어:

```text
목도리 → 머플러
```

- 검토 큐의 번역은 사용자 검토 완료본을 정본으로 반영한다.
- 번역 중간 검증을 반복하지 않고 전체 번역 후 검토 항목을 모아 최종 확인하는 방식으로 바꿨다.

### 5.4 대사 번역 및 출력

- 대사 부분의 한글 출력은 여러 화면에서 확인했다.
- 사용자가 대사 번역 검토를 여러 차례 완료했다.
- 난이도 선택 화면과 일반 대사창에서 한글 표시를 확인했다.
- 일본어 원문의 고정폭 또는 글자 advance를 그대로 사용해 한글 글자 사이 공백이 과도하게 넓었다.
- 한글 폭을 줄이는 조정을 적용했고 사용자가 실제로 폭이 줄어든 것을 확인했다.
- 2줄 대사 출력도 정상 확인했다.
- 사용자가 다음 대사를 직접 수정했다.

```text
자, 기한은 내일 아침까지야.
```

- 화자 이름 말풍선은 폭이 고정되어 번역 이름이 원문보다 길면 넘어간다.
- 원문보다 긴 화자명 또는 번역 문자열 목록을 추려 단축하는 작업이 필요하다.

### 5.5 대사에서 남은 버그

1. 쉼표가 표시되지 않거나 간격이 부자연스러운 사례가 있었다.
2. `!`, `?`, `…` 등 특수문자와 앞 글자 사이 간격이 너무 좁다.
3. 대사 표시 직후 이상한 한자나 문자가 섞여 나타난다.
4. 버튼을 한 번 누르면 이상 문자가 사라지는 경우가 있다.
5. 글자폭 문제와 별개로 초기 버퍼 정리, 문자열 종료, 제어코드 또는 이전 프레임 글리프 잔존 문제일 가능성이 있다.

다음 조사 시 다음 순서로 확인한다.

1. 문자열 종료 코드와 버퍼 길이
2. 줄바꿈 삽입 후 남는 기존 바이트
3. 대사 버퍼를 새 문자열 길이만큼만 덮고 나머지를 지우지 않는지
4. 글리프 캐시 또는 텍스처 캐시 갱신 타이밍
5. 쉼표와 문장부호의 매핑 및 advance 테이블

## 6. 타이틀 화면 작업

### 확정 문구

```text
프리니
~제가 주인공해도 되겠슴까?~
```

### 확정 디자인 규칙

- `프리니`만 한컴 말랑말랑 Bold 계열로 두껍게 표시한다.
- 나머지 메뉴, 부제, 시스템 글자는 Bold로 바꾸지 않는다.
- `프`, `리`, `니`는 동일한 크기와 동일한 기준선에 배치한다.
- 빨간 리본과 평행하도록 기울인다.
- 글자 상단 기준은 `프`의 `ㅍ` 윗부분과 `리`, `니`의 모음 `ㅣ` 윗부분을 맞춘다.
- 원문 글자의 흰색 잔재는 모두 제거한다.
- 반투명한 얇은 외곽선을 적용했다.

### 최종 사용자 승인값

- `리` 각도: 21도
- 최종 상태에서 `니`만 1 텍스처 px 위로 이동
- 사용자가 “이걸로 확정”이라고 승인했다.

### 기타 메뉴

- `데이터 로드`와 `데이터 교환`은 동일한 폰트 두께를 사용해야 한다.
- `프리니`만 Bold이며 나머지 글자가 함께 굵어지지 않도록 한다.

## 7. 튜토리얼 카드 작업

### 공통 원칙

- 제목은 좌우 삼각형 사이의 시각적 중앙에 배치한다.
- 빨간 강조 글자는 원래 크기를 유지한다.

- 괄호 위치와 강조 글자 위치를 각각 움직여 중앙에 맞춘다.
- 버튼 아이콘과 뒤따르는 글자 간격을 충분히 확보한다.
- `[]`는 실제 표시되는 일본식 괄호 형태의 위치와 높이를 맞춘다.

### 조정한 항목

- 튜토리얼 점프
- 튜토리얼 공격
- 베기 공격
- 프리니 연사
- 튜토리얼 웅크리기
- 튜토리얼 적 기절
- 튜토리얼 들기·던지기
- 튜토리얼 보스전
- 실드 카운터

### 반복 발생한 문제

- X 버튼이 뒤 글자와 겹치거나 간격이 너무 좁음
- □ 버튼과 뒤 글자 간격 불균형
- 점프, 베기 공격, 프리니 연사, 웅크리기, 적 기절, 들기, 던지기가 괄호 중앙에 맞지 않음
- `던지기`를 축소했을 때 흐릿한 잔상이 생김
- 들기·던지기에서 괄호가 2개 표시되거나 `가능!`이 깨짐
- 보스전에서 해골 아이콘이 2개 표시됨
- 실드 카운터와 해골 아이콘, 괄호 위치가 맞지 않음

### 현재 판단

- 여러 항목은 사용자가 화면을 보며 조정했고 부분 승인했다.
- 이후 다른 빌드에서 중복 아이콘과 괄호 문제가 다시 보였다.
- 따라서 튜토리얼 카드 전체는 `부분 완료 / 최종 전수 재검증 필요` 상태다.

## 8. 이미지 및 ANIME.DAT 조사

### ANIME.DAT PNG의 성격

- ANIME.DAT에서 추출한 PNG는 영상 프레임이 아니라 게임에서 사용하는 텍스처 레코드 또는 애니메이션 아틀라스다.
- 하나의 PNG 안에 여러 UI 조각, 글자, 아이콘이 포함될 수 있다.
- 실제 게임에서는 UV 좌표, 팔레트(CLUT), 레이어 조합으로 일부 영역만 사용한다.
- 같은 픽셀 데이터라도 CLUT가 다르면 화면의 색과 역할이 달라질 수 있다.

### 이미지 초벌 번역

- 이미지 전체를 개별 플레이로 찾는 방식이 느려 검수 갤러리를 만들었다.

## 10. 데모 스킵 문제

### 원본 추출 파일

```text
066_start.dat_anime00.dat_record-87_texture-0.png
```

### 증상

- `△ 데모 스킵` 글자가 깨지고 여러 흰색 조각이 겹쳐 보인다.
- 하나의 번역 PNG만 바꿔서는 정상 표시되지 않았다.

### 확인된 원인

- 같은 텍스처 hash `f4cbdbb1`을 사용하는 128x128 CLUT4 레이어 3개가 겹친다.
- 픽셀 데이터는 같거나 유사하지만 CLUT/주소가 서로 다르다.
- 각 레이어가 흰색 본문, 외곽선, 강조색 등 서로 다른 역할을 할 가능성이 높다.

```text
091cd1e0f54138b2f4cbdbb1.png
091cd1e0f96c6b82f4cbdbb1.png
091cd1e0a8d5fd96f4cbdbb1.png
```

### 다음 해결 방식

1. 세 CLUT 변형을 모두 덤프한다.
2. 각 팔레트에서 어떤 인덱스가 본문, 외곽선, 투명 영역인지 비교한다.
3. 동일한 흰색 완성 이미지를 세 파일에 복사하지 않는다.
4. 각 레이어의 역할에 맞는 마스크만 남긴다.
5. PPSSPP 텍스처 교체로 세 레이어 조합을 먼저 검증한다.
6. 정상 조합을 찾은 뒤 원본 ANIME.DAT에 팔레트 인덱스를 유지한 상태로 삽입한다.

## 14. 스테이지 결과 화면

### 증상

- `클리어 시간` 뒤의 시간 숫자에 트로피 아이콘이 겹친다.
- `%02d′%02d″%02d` 형식이 정상 표시되지 않는다.
- `사망 프리니 수` 뒤 단위가 `마리`가 아니라 한문 또는 잘못된 글자로 표시된다.
- 우측 합계도 `마리` 표시가 깨진다.

### 판단

- 단순히 폰트에 숫자가 없어서 생긴 문제만은 아니다.
- 시간 구분용 prime 글리프 `′`, `″`가 아이콘 코드와 충돌하거나 잘못 매핑됐을 수 있다.
- 포맷 문자열의 제어코드 또는 글리프 인덱스가 번역 과정에서 변경됐을 수 있다.
- `마리`는 폰트에 존재해도 원문 단위 코드가 그대로 남아 다른 글리프를 가리킬 수 있다.

### 다음 작업

1. 원문 결과 화면 포맷 문자열의 정확한 바이트열을 찾는다.
2. `%02d` 토큰과 제어코드를 보존한 채 번역한다.
3. `′`, `″` 대신 게임이 원래 사용하던 구분 코드를 유지한다.
4. 트로피 아이콘 코드와 문자 코드 범위를 비교한다.
5. `匹` 또는 원문 단위가 있는 위치를 찾아 `마리`에 대응하는 한글 인코딩으로 바꾼다.

## 16. 기존 통합 ISO가 실패한 이유

현재 통합 ISO에서는 다음이 확인됐다.

- 텍스처 교체에서만 보이던 번역 이미지가 ISO 내부에는 들어가지 않음
- 튜토리얼 푯말이 일본어
- `△ 데모 스킵`이 깨짐
- 시스템 메뉴가 일본어
- 스테이지 결과 시간과 단위가 깨짐
- 스테이지 설명이 모두 같은 번역으로 나오거나 혼합됨
- 일부 동적 텍스트를 정적 PNG로 잘못 처리함

가능성이 높은 원인:

1. 여러 빌드 스크립트가 서로 다른 기준 트리를 사용했다.
2. translated PNG를 ISO의 실제 DAT 레코드에 다시 삽입하지 않고 PPSSPP 텍스처 팩에만 배치했다.
3. 이미 변경된 트리에 또 패치를 적용해 레코드와 포인터가 어긋났다.
4. stage info 문자열 패치와 이미지 패치의 적용 순서 또는 소스가 일치하지 않았다.
5. 최종 ISO 전 단계에서 파일별 diff와 삽입 검증을 하지 않았다.

따라서 기존 통합 ISO는 폐기 대상이며, 앞으로 clean extracted 기반의 직접 실행 폴더에서 먼저 통합 검증한다.

- `7c2b8daf...` 빌드에서 음성 설명은 반복 선택 후에도
  `【이벤트】 음성 메시지 음량을 바꿉니다.`로 정상 유지되었다.
- SE/BGM은 `【이벤트】 시 지 ... 음량을 바꿉니다.` 형태로 서로 같은 오염 문구에
  고정되었다.
- 카메라는 `【전이벤트】 시 지율 바 ... 정상시다.`처럼 다른 문장의 글리프가
  합쳐졌다.
- 이전처럼 선택할 때마다 계속 다른 깨진 값으로 변하지는 않았지만, 최초 오염 뒤
  잘못된 조합이 고정되는 상태였다.

### 새 원인 가설과 적용

- 프레임 끝의 기존 리셋은 페이지별 캐시 개수만 0으로 만들고 864바이트 캐시 본문은
  지우지 않았다.
- 공통 렌더러 안에 캐시 기록 훅을 통과하지 않는 별도 문자 경로가 있으면 캐시 인덱스에
  기록되지 않은 구멍이 생길 수 있다. 다음 프레임에 그 구멍의 이전 글리프 ID가 남아
  있으면 잘못된 중복 적중과 atlas cell 재사용이 발생한다.
- `0x0888E22C` 리셋 헬퍼에서 페이지 0/1 캐시의 연속 864바이트를 216회 word store로
  실제 0 초기화하도록 변경했다.
- 리셋 헬퍼가 추가로 사용하는 `$t0/$t1`은 스택에 보존하고 복원한다.
- 자동 테스트 110개 PASS, BOOT UI 슬롯 560/560 PASS.

## 39. 두 번째 렌더러 페이지 전환 누락 보완

### 사용자 런타임 결과

- 캐시 본문 초기화 빌드에서도 처음 약 2회는 정상 표시되지만 이후 SE/BGM/카메라
  설명이 잘못된 조합으로 바뀌고, 그 뒤에는 같은 오염 값으로 고정되었다.
- 음성 설명은 반복 선택 후에도 정상 유지되었다.
- 따라서 번역문 길이 초과나 매 선택마다 누적되는 단순 버퍼 오버런보다는, 특정
  렌더링 경로에서 페이지별 atlas 상태가 한 번 어긋난 뒤 재사용되는 현상과 일치한다.

### 확인된 원인 후보
